## 2. 网关做什么

`jasagent-gateway` 是独立的 Spring Boot 进程，使用 Spring Cloud Gateway MVC（`spring-cloud-starter-gateway-mvc`，BOM 2024.0.3），不是 WebFlux。它打包成可执行 jar。

对外监听默认是 `127.0.0.1:18721`。浏览器只访问网关。登录、会话、`/admin` 控制台、`GET /api/me`、`GET /api/cluster` 和 `GET /health` 留在网关进程。其余 `/api/**` 按粘性转发到 agent。注释和测试都写明：agent 不再提供登录页和控制台，也不再接受用户登录，只核对内部令牌。

本机默认把请求转到 `127.0.0.1:18731` 和 `127.0.0.1:18732`。实例编号固定为 `agent-{端口}`，例如 `agent-18731`。K8s 清单里用环境变量 `JASAGENT_GATEWAY_AGENTS` 改成两台 agent 的集群 DNS 和端口，编号仍按端口生成。

本机多进程启动走 `scripts/sandbox/start-gateway.sh`：先打包 `jasagent-gateway`，再在宿主机跑 jar，因为网关要读本机 MySQL 口令文件，脚本刻意不把网关放进容器。K8s 里网关镜像仍走 `deploy/k8s/Dockerfile` 和 `entrypoint.sh`；入口脚本只认 `/opt/jasagent/jasagent-app.jar`，并把监听改成 `0.0.0.0`。构建时要把网关 jar 按这个文件名放进去。

模块依赖是 `jasagent-api`、`jasagent-trace`、`jasagent-auth`，再加上 MySQL 驱动 `mysql-connector-j` 9.2.0 和 Spring Boot 测试。

## 3. 关键机制

### 3.1 登录和会话

网关用 `jasagent-auth` 的 `LocalAuthService`，口令规则仍是用户目录里的 PBKDF2。不提供自助注册，第一个用户仍由本机命令创建。

会话 Cookie 名是 `JASAGENT_SESSION`，`HttpOnly`、`Path=/`、`SameSite=Lax`，没有 `Secure`。也可以用 `Authorization: Bearer`。`/api/**` 没有会话时返回 401 和 `{"executionId":null,"errorCode":"AUTH"}`。其它未登录页面重定向到 `/admin/login`。`GET /` 转到 `/admin/`，`GET /login` 转到 `/admin/login`，`POST /login` 仍是登录接口。

`GatewaySessionFilter` 把 `/admin` 和 `/admin/**` 全部列为匿名可访问。静态资源和登录页因此能打开；真正的业务接口仍要会话。这是有意放行页面，还是过滤范围过宽，需要确认。

为了避开 Spring Cloud Gateway 表单过滤器先读正文的问题，`LoginFormFilter` 以最高优先级缓存 `POST /login` 的表单，登录结束后清掉口令字符数组。

### 3.2 粘性路由和存活探测

粘性键是 `(tenant_id, user_id)`，不是会话，也不是 execution。默认租户是 `local`。同一登录名的请求会粘到同一台仍存活的 agent。目标实例的长连接还在时不改道；断开后改到当前存活实例里端口最小的一台，并写回 MySQL。两台都断开时抛出内部错误，但保留原粘性行，实例恢复后还能粘回去。已改道的用户，即使原实例恢复，也不会迁回。

粘性表是本机库 `jasagent` 中的 `jasagent_gateway_affinity`。JDBC 地址写死为 `127.0.0.1:3306/jasagent`，账号写死为 `root`。口令只从仓库外的 `$HOME/.config/urag-mysql-root.password` 读取，文件名仍带旧前缀 `urag`。地址里若带 `password=` 会直接拒绝。异常和 `toString()` 都不附带口令或数据库原文。

这个粘性库在 Spring 装配时就会 `openDefault()`。本机没有口令文件时，网关进程起不来。

存活状态在进程内的 `InMemoryAgentLiveness`，由 `TcpAgentLink` 长连接维护。它不进 MySQL。因此当前设计天然适合网关单副本。K8s 里 `deploy/k8s/gateway.yaml` 也确实是 `replicas: 1`，并在同 Pod 里放 `mysql-bridge`，把集群 MySQL 转到容器回环的 3306，以迁就写死的 `127.0.0.1`。

### 3.3 转发给 agent 的约定头

调用 agent 时只使用四个约定头，名字不能另起：

- `X-Jasagent-Token`：值只来自环境变量 `JASAGENT_INTERNAL_TOKEN`，未配置则拒绝转发，返回 503
- `X-Jasagent-Tenant`
- `X-Jasagent-User`：登录名
- `X-Jasagent-Session`：路径里的会话编号；路径没有会话时才用登录会话文件名。这不是 Cookie 里的登录令牌

转发前会清掉浏览器带来的 Cookie、`Authorization`，以及旧名字的内部头。令牌对象的 `toString()` 只说明是否已配置，不打印原文。

### 3.4 响应改写和溯源

`GET /api/models` 会在转发后补上 `deepseek-flash` 和 `grok-4.7`，已有则不重复。执行详情、中断、恢复和通行证决定的 JSON 会写上这次落到的 `agentInstanceId` 和 `agentAddress`，并覆盖 agent 自己带的同名字段。事件流不改写，避免把长连接响应整段读进内存。

新建执行（`POST /api/executions` 或 `POST /api/sessions/{id}/messages`）成功后，按 `executionId` 把租户、用户、会话和 agent 记进溯源。写失败不影响这次转发，也不把异常原文写进日志。直接提交执行、路径上没有会话时，溯源里的会话会用这次 `executionId`。

`GET /health` 只表示网关进程自己起来了，不代表 agent 长连接可用。

### 3.5 管理页

`/admin/**` 挂的是 `jasagent-gateway/src/main/resources/gateway-admin/` 下已经构建好的静态产物（含较大的 js/css）。`GatewayAdminStaticMount` 的注释写明：agent 启动类只扫描 `dev.jasagent.app`、`dev.jasagent.controller`、`dev.jasagent.web`，不会加载这份页面。

团队规则是：界面相关改动只允许落在 `jasagent-web`，不得另起或改用其他前端。仓库里现在已经有一份打进网关模块的管理控制台。这是当前块里最需要先对齐的产品/边界问题。

## 5. 风险

1. 实现已合入，但正式调研、四人评审和 Hang 确认还没有走完。默认分支还是 Cursor 实现分支，没有 `main`。
2. 管理控制台静态资源落在 `jasagent-gateway`，和“界面只改 `jasagent-web`”的规则冲突。
3. `/admin/**` 在会话过滤器里全部匿名放行。若控制台里还有不该公开的页面或接口，只靠前端自己保护是不够的。
4. 粘性库地址和账号写死，存活探测只在进程内存。水平扩展网关、换数据库地址或跑多副本，都会碰壁。K8s 用 mysql-bridge 和单副本来迁就现状，但这属于部署块的后续问题，当前只作为网关设计约束记下来。
5. 本机存在两套 18721 入口：`scripts/start.sh` 仍启动 `jasagent-app`，`scripts/sandbox/start-gateway.sh` 才启动网关。README 目前只写了前者。两边抢同一个端口。
6. 网关启动强依赖本机（或同 Pod 回环）MySQL 口令文件。口令文件名仍是 `urag-mysql-root.password`。
7. `StickyAgentRouterTest` 依赖真实 MySQL 和口令文件，在没有这套本机环境的地方跑会失败。
8. 模型目录由网关改写，等于网关承担了一部分模型发现策略。这和 LLM 路由模块的边界要不要分开，需要确认。
9. 变更记录写容器内 Grok 调用曾经超时，宿主机测试是通的。这不一定是网关缺陷，但说明“经网关访问模型”的端到端验证还不完整。

## 6. 可选方向（只列选项，不拍板）

- 管理页：继续把构建产物打进网关；或由 `jasagent-web` 构建、网关只挂产物；或控制台仍由 `jasagent-web` 提供、网关只做反向代理。
- 粘性存储和存活探测：维持“MySQL 粘性 + 进程内存存活 + 网关单副本”；或把 JDBC 做成可配置并拿掉对 `127.0.0.1` 的硬编码；或把存活状态也做成可共享。这些若要改，也只应在确认后由实现角色做。
- 本机启动：继续保留单进程 `start.sh` 和网关沙箱脚本两套入口，但把 README 写清楚；或让日常 `start.sh` 改为拉起网关和 agent。
- 需求文档：确认后把已对齐的内容整理为 `requirements/` 下的网关需求；或先维持 changelog 加本调研笔记，等整块评审过后再写。

## 8. 调研意见（供评审，不是块通过结论）

从调研角度看，网关块在仓库里已经是一套可描述、有测试、有变更记录的实现：职责边界清楚，内部头和粘性规则写得很明确，口令与令牌也不进仓库。主要风险不在“有没有网关”，而在三件事：实现先于确认；管理页落点与界面规则不一致；本机启动路径和写死的数据面约束还没有正式对齐。

在上述问题 1、2、6、9 没有答复之前，调研不建议把本块视为可以结束评审并进入 sidecar 的状态。这不是对实现质量的否决，而是范围和规则还没对齐。
