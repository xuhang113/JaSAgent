# agent 等待和恢复不再占用 Tomcat 平台工作线程

- 日期：2026-11-19（Asia/Shanghai）
- 做了什么：agent 仍是 Spring MVC + Tomcat，没有改成 WebFlux。等待 sidecar、模型流和工具，以及 HTTP 上的 resume / interrupt，都不再占着 Tomcat 的操作系统平台工作线程。容器线程对恢复和中断只开启 Servlet 异步，随后在虚拟线程上等待；模型流在调用方的虚拟线程上按块解析。agent 侧出站不再使用会在 `synchronized` 里读流、从而在 Java 21 上钉住载体的 JDK 默认响应体处理器，改成有界队列把已到达的一块交给读线程。请求体和响应体仍按块传递，不把整段读进内存后再转发。`/v1/forward` 的方法、路径、目的地址头、票据头、流式正文和不跟随重定向保持不变。会话、租户和权限随异步任务带走：请求线程上的身份在移交前抄下来，路由到模型的虚拟线程和图节点按执行编号再绑一次，执行结束时清掉，不留在下一次请求上。执行状态和检查点控制器改用可重入锁，等日志或检查点存储器时不再因为 `synchronized` 把虚拟线程钉在载体上。生产默认 `jasagent.app.tomcat-platform-workers=0`，不替换 Tomcat 线程池，也不压低生产上限。验收才把这个操作系统平台线程数降下来。它不是 `server.tomcat.threads.max`。
- 涉及模块：jasagent-llm、jasagent-app、jasagent-workflow、jasagent-controller、jasagent-interrupt、scripts。不改 jasagent-sidecar、jasagent-gateway、jasagent-web，不改 deploy/k8s。
- 怎么验证：`bash scripts/test-022-runtime-full-async.sh`。脚本覆盖验收第 1 到第 9 条：`jcmd Thread.print` 核对 jasagent-app 的操作系统平台线程（线程名 `jasagent-app-platform-`，带 nid，停在线程池取任务），`server.tomcat.threads.max` 保持 64，平台工作线程压到 2，并发 6 路长 ReAct（含恢复）超过该上限，首块在上游结束前到达，期间 `/health`、新的提交和新的发消息在超时内可用；两个租户并发时会话、租户和权限不丢失也不串；复跑 018（对比底改为 origin/master）和 sidecar 模块测试。钉载体的判定是日志里的 `Pinned:`，以及 `reason:MONITOR` 栈里出现 `dev.jasagent`。SQLite 驱动第一次装载本地库时自己的监视器可能打出一行，栈里没有本轮代码，脚本只计数、不把它当成失败。验收进程另外带上 `--add-opens java.base/java.net=ALL-UNNAMED` 和 `--add-opens java.base/jdk.internal.loader=ALL-UNNAMED`，只为让现有检查点存储器在 Spring Boot 胖包里打开 SQLite；这不是生产默认，也不改 jasagent-persist。未改动的 021 脚本自带路径白名单，只允许 sidecar 那一轮的文件，本轮运行时差异会被它拒绝，所以不把它的白名单放宽，也不用它的退出码代替本轮证明。第 10 到第 12 条留给部署，本记录不代替 ATDD，也不写 deploy.md。
